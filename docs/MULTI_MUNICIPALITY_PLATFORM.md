## Phase 1 — نموذج البلديات والحسابات والصلاحيات
- `src/municipalities.js`: البيانات الموثقة، `defaultAssignmentFor/municipalityForNeighborhood`، أدوار قانونية (`PLATFORM_ADMIN = executive`, `MUNICIPALITY_MANAGER = manager`, `OPERATIONS_EMPLOYEE = employee`, `DRIVER`)، `scopeFor/inScope`، `computeMunicipalityStats`، `operationalZones`.
- `municipalityId` مُنسَّخ على: الأحياء، الحاويات، الجولات، المركبات، ملفات السائقين، البلاغات، مواقع السائقين (`seedMunicipalitiesAndBackfill` من الإعدادات، وكل مسار كتابة جديد).
- **عزل البيانات خادميًا** في `firestore.rules`: `scoped()/sameMun()` — المدير/الموظف/السائق بمعرّف بلدية لا يقرأ ولا يكتب إلا صفوف بلديته (والاستعلامات مقيدة بـ`where municipalityId ==` في `useScopedCollection`)؛ مدير بلا بلدية بلا وصول تشغيلي؛ تبعية الأحياء ومجموعة البلديات لمدير المنصة فقط.
- التسجيل: دور «مدير بلدية» + اختيار البلدية للمدير/الموظف/السائق؛ إدارة المستخدمين: تعيين البلدية.
- حسابات العرض: `scripts/createDemoAccounts.mjs` (Admin SDK، كلمة المرور من `DEMO_PASSWORD` فقط): admin / manager.east / manager.north / ops.east / driver.east @demo.smartwaste.local.
- وضع المحاكي المحلي: `VITE_USE_EMULATOR=1 npm run dev` + `firebase emulators:start --only auth,firestore` (firebase.js).

## Phase 2 — صفحات البلديات والخرائط
- «البلديات والنطاقات التشغيلية»: 6 بطاقات (أحياء، حاويات، % متصلة بالمحاكي، حرجة، سائقون متاحون، مركبات نشطة، جولات جارية، مقترحة، حالة التشغيل؛ الحرجة لا تُخفى خلف المتوسط).
- لوحة البلدية: الخريطة (مقيدة بالبلدية + نطاقها)، الأحياء (الاسم الرسمي ✓/⚠️، درجة ثقة التبعية والدليل، تعديل الاستثناء التشغيلي لمدير المنصة)، الحاويات والمستشعرات، السائقون والمركبات، الجولات، البلاغات، مؤشرات الأداء + الأثر.
- الخريطة: طبقات (البلديات / الأحياء / الحاويات / الجولات والمركبات)، نطاقات البلديات بخط متقطع وشفافية 0.12، ألوان 60/85 للحاويات والأحياء (من المرحلة السابقة).
- الشارة الدائمة: «بيئة عرض تجريبية — بيانات المستشعرات محاكاة». «متصل بالمحاكي» بدل «متصل» لكل مستشعر افتراضي. قسم مصادر البيانات في الإعدادات بحالة كل مصدر.
- مدير المنصة يستخدم الصدفة التشغيلية الكاملة وبوابة متخذي القرار صفحة داخلها.

## Phase 3 — محاكي المستشعرات
- `src/simulation/simulationEngine.js` (نقي، حتمي): PRNG مزروع، 120 حاوية داخل مضلعات الأحياء (رفض عينات)، 108 متصلة / 8 منقطعة / 4 معطلة، مزيج امتلاء 55/30/15، 3 تنبيهات حرارية، بطاريات، آخر اتصال؛ `advance` (معدل امتلاء لكل حاوية، انجراف حرارة، نضوب بطارية)؛ أحداث: امتلاء حرج، ارتفاع حرارة، انقطاع، خلل، تفريغ، عودة. كل قراءة: `binId, sensorId, fillPercentage, temperature, batteryLevel, connectivityStatus, timestamp, source=SIMULATED` (+ أسماء بديلة للمحركات القائمة).
- `simulationRunner.js`: يكتب فقط في حاويات `simulated:true` و`simulated_readings`؛ `sensor_readings` الحقيقية لا تُكتب من أي عميل (قاعدة). تثبيت/إعادة ضبط حتمي، بدء/إيقاف، تسريع 1–60×، نافذة قائدة للنبضات مع تولّي عند التعطل، تاريخ 3 قراءات لكل حاوية لتفعيل التنبؤ، تاريخ أسطول اختياري.
- صفحة «المحاكاة (عرض)»: الإعدادات التجريبية، التحكم، الأحداث حسب البلدية/الحاوية، سجل النبضات والأحداث.

## Phase 4 — الربط الكامل
نفس الحقول التي يكتبها مسار الأجهزة الحقيقي → لوحة التحكم، الخريطة، الحاويات، محرك الأولوية، التنبؤ (يقرأ `sensor_readings` + `simulated_readings`)، اقتراح الجولات (مزامنة تلقائية)، الإسناد، بوابة السائق، سجل التفريغ، التقارير. تأكيد السائق التفريغ → صف `collection_events` (تشغيلي) → في النبضة التالية قراءة SIMULATED بسبب `emptied` (منفصلة). الترتيب المحسَّن للجولة يُحفظ عند المزامنة التلقائية ويُوسم `stale` عند إضافة حاويات.

## Phase 5 — وضع العرض
`src/demoScenario.js` + صفحة «سيناريو العرض»: كان 12 خطوة، وأصبح **21 خطوة** في مرحلة التحول المؤسسي (انظر `docs/ENTERPRISE_PLATFORM_REPORT.md`). الخطوات الأصلية: (المدينة → اختيار بلدية → الأحياء والحاويات → 3 أحداث امتلاء → اكتشاف الحرجة → اقتراح جولة + تحسين ترتيبها → ترشيح سائق (تهيئة تلقائية لسائق البلدية: مركبة، نطاق، مناوبة) → اعتماد → ظهورها للسائق → الملاحة → التفريغ → المؤشرات). الحالة في `demo_sessions/current` (ثابتة عند التحديث، إكمال أحادي الاتجاه)، وإعادة من البداية تعيد تثبيت المشهد بنفس الـseed.

## Phase 6 — الاختبارات
- وحدة: 171 اختبارًا (منها: بيانات البلديات والتبعية، الأدوار والنطاق، المحاكي الحتمي والأداء (1,000 حاوية × 100 نبضة < 2 ث) وإعادة التشغيل، السيناريو، الطابور دون اتصال، الملاحة، التنفيذ).
- قواعد Firestore على المحاكي: 13 سيناريو (`npm run test:rules`) تشمل عزل البلديات والمدير بلا بلدية والقراءات المحاكاة.
- تحقق متصفح (Playwright على المحاكي المحلي): عزل المدراء، صفحة البلديات ولوحتها، تثبيت حتمي (إعادة الضبط تعطي القيم نفسها)، النبضات والأحداث، انعكاسها في لوحة التحكم (14 حيًا تحتاج جمعًا، 14 جولة مقترحة)، السيناريو الكامل حتى تنفيذ السائق وقراءة التفريغ.

## القيود المتبقية
- حدود البلديات غير رسمية في النظام (قابلة للاستبدال بملف GeoJSON رسمي عند توفره: `operationalZones` تُستبدل بمضلعات حقيقية).
- مواقع الحاويات الافتراضية داخل الأحياء بلا التصاق بالطرق (لا بيانات طرق محلية؛ خدمة OSRM `nearest` ممكنة لاحقًا).
- نبضات المحاكي تحتاج نافذة متصفح مفتوحة لحساب مسؤول؛ لا مهمة خلفية في Vercel.
- الموظفون الحاليون بلا `municipalityId` يُعامَلون غير منطاقين (وضع انتقالي موسوم `legacy`) حتى تُعيَّن بلدياتهم.
- القواعد الجديدة وحسابات العرض لم تُنشر؛ للإنتاج: `firebase deploy --only firestore:rules` ثم `FIREBASE_SERVICE_ACCOUNT_JSON=… DEMO_PASSWORD=… node scripts/createDemoAccounts.mjs` ثم «تهيئة البلديات» و«تثبيت المشهد» من حساب مدير المنصة.
