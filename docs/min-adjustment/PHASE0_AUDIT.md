# المرحلة صفر — فحص النسخة الحالية قبل محرك الحد الأدنى للتعديل التشغيلي

**المرجع:** الالتزام `704311d` على الفرع المحلي `feature/min-operational-adjustment`.
**الطريقة:** تتبّع مسار القرار بالترتيب التالي:
1. قراءة المستشعر.
2. الخادم: `runDispatchCycle`.
3. المحرك النقي: `planDispatch` ثم `analyzeResourceGaps`.
4. Firestore: `dispatch_decisions` و`collection_routes`.
5. الواجهة: `OpsDataContext` ثم `DecisionCard` و`CoverageRecommendations`.

## 2. الوظائف الناقصة
1. **لا يوجد مقيّم جدوى موحد.** كل محرك يتحقق من جزء من القيود:
   - `assignmentEngine`: المناوبة والسعة.
   - `resourceGapEngine.SHIFT_TIMING`: لا يفحص السعة ولا نهاية المناوبة.
   - `decisionSimulator`: عبر `collectionPlanner`.
   - لا يوجد زمن تفريغ، ولا عودة للمستودع، ولا فحص التزامات الجولة التالية بعد بدء المناوبة.
2. **لا يوجد بحث عن «أقل تعديل».** السلّم ثابت الترتيب، ويختار أول خيار يحقق الهدف. لا مقارنة تكلفة، ولا تركيبات، ولا حالة محسِّن.
3. **لا توجد حالات جدوى صريحة:** `FEASIBLE` / `PROVEN_INFEASIBLE` / `NO_SOLUTION_FOUND` / `TIME_LIMIT` / `INSUFFICIENT_DATA` / `ERROR`.
4. **لا اعتماد خادميًا للتوصية،** ولا فصل بين `SIMULATED` و`PROPOSED` و`APPROVED` و`EXECUTED`.
5. **لا سجل يربط التعديل المعتمد بنتيجته.**
6. **لا حجوزات زمنية للموارد المعارة،** ولا فحص للجهة المعيرة طوال فترة الإعارة.

## 4. التعارضات بين المحركات
- **المسافة:** ثلاثة مقاييس مختلفة:
  - جوي في `expectedRouteImpact`.
  - جوي مع مصفوفة OSRM في `routeOptimizer`.
  - طرق في `computeRoadTravel`.

  لا يحمل الرقم المعروض نوع المقياس دائمًا.
- **زمن المهمة:** ثلاثة مصادر مختلفة لا تتطابق:
  - `resourceGapEngine` يحسب حجم العمل جويًا مع زمن الخدمة.
  - `assignmentEngine` يستخدم `estimatedDistanceKm` للجولة.
  - `collectionPlanner` له نموذجه الخاص.
- **الضغط التشغيلي مقابل الجدوى:** `interMunicipalEngine` يحكم على سلامة الجهة المعيرة بمؤشر ضغط عام (`donorCeiling`)، لا بالتزاماتها الفعلية.
- **التكلفة:**
  - `decisionSimulator` يحوّل الكيلومترات والدقائق إلى ريال بافتراضين معلنين (`fuelPricePerLiter` و`crewCostPerHour`).
  - `interMunicipalEngine` يستخدم «نقاط ضغط» مع دقائق.

  لا يوجد نموذج تكلفة واحد.

## 5. البيانات المطلوبة للتطوير وما ينقصها

| البيان | متاح؟ | الأثر عند غيابه |
|---|---|---|
| سعة المركبة `capacityLiters` | غالبًا | سعة مجهولة تعني أن القيد غير قابل للإثبات (`missingData`). لا تُعدّ صالحة |
| نافذة المناوبة `shiftStart/shiftEnd` | للسائقين المهيئين | مجهولة تعني أن قيد نهاية المناوبة غير قابل للإثبات |
| نقطة الانطلاق | موقع مباشر، أو مستودع المركبة، أو نهاية الجولة | غيابها يجعل الطاقم غير قابل للتقييم (`INSUFFICIENT_DATA`) |
| نقاط التفريغ | **غير موجودة في البيانات** | الحمولة الزائدة عن السعة تعني حالة غير ممكنة، ولا يُفترض موقع تفريغ |
| زمن التفريغ | غير موجود | سياسة قابلة للضبط (`unloadMin`)، ويُستخدم فقط إذا عُرّف موقع تفريغ |
| اشتراط العودة للمستودع | غير موجود | سياسة قابلة للضبط (`returnToDepotRequired`، الافتراضي `false`) |
| تكاليف مالية موثقة | **غير موجودة** | التكلفة المالية «غير متاحة»، أو معامل تجريبي موسوم في بيئة المحاكاة فقط |
| مسافة GPS فعلية | غير مسجلة لكل جولة | «الوفر الفعلي غير متاح» |

## 6. مخاطر أمنية
- **اعتماد التوصيات:** سيضيف مسارًا خادميًا جديدًا يعدّل الجولات والموارد. يجب أن يمر بـ`guard` (الهوية، والدور، والبلدية، و`rate limit`)، ومعاملة ذرية، وidempotency.
- **اعتماد النقل:** يتم اليوم من العميل (القاعدة تسمح للأمانة بتحويل `proposed` إلى `approved`). الحجز الزمني الجماعي يحتاج نقل الاعتماد إلى الخادم، وتضييق القاعدة.
- **المجموعات الجديدة:** `adjustment_analyses` و`resource_reservations` تُكتب من الخادم فقط، وتُقرأ داخل البلدية.
- **قاعدة ثابتة:** لا يُسمح للعميل بتمرير الخطة أو الأرقام. الخادم يعيد بناء اللقطة ويعيد الحساب.
