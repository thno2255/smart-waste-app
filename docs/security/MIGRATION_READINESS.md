# جاهزية ترحيل `municipalityId` — `scripts/migrations/backfill-security-scope.mjs`

> **الحالة:** جاهز ومختبَر على المحاكي فقط. **لم يُشغَّل على الإنتاج.** تشغيله على الإنتاج يحتاج موافقة صريحة من مالك المشروع.

## 1. ماذا يفعل الترحيل
القواعد الحالية تُغلق عند غياب البلدية (fail-closed): طاقم البلدية يرى المستند فقط إذا كان `municipalityId` فيه يساوي بلديته. المستندات القديمة التي لا تحمل الحقل تختفي عن الطاقم وتبقى ظاهرة للأمانة فقط. لذلك يضيف الترحيل الحقل للمستندات التي يمكن استنتاج بلديتها بيقين:

| المجموعة | مصدر البلدية |
|---|---|
| `requests` | اسم الحي ← `neighborhoodMunicipalityMap.json` |
| `citizen_reports` | بلدية الحاوية `binId`، وإن تعذّرت فاسم الحي |
| `alerts` | بلدية الحاوية أو الحي `sourceId` |
| `iot_devices` | بلدية الحاوية `binId` |
| `collection_events` | بلدية الجولة، وإن تعذّرت فبلدية الحاوية |
| `vehicle_status_history` | بلدية المركبة |

المستند الذي لا تُستنتج بلديته **لا يُخمَّن**. يُدرج في التقرير ضمن `unresolved` مع معرّفاته، ويبقى ظاهرًا للأمانة فقط.

## 2. ضمانات الأمان

| المتطلب | التنفيذ | الاختبار |
|---|---|---|
| Dry Run افتراضيًا | بدون `--apply` لا يُكتب شيء، ويُطبع تقرير التغييرات المتوقعة | `admin.users.test`: «dry run writes nothing + reports» |
| نسخة احتياطية قبل الترحيل | `--apply` **يرفض العمل** دون `--backup <dir>`. قبل أي كتابة يحفظ `backup-<ts>.json` بكل مستند سيتغير وقيمه السابقة | «apply needs a backup» + فحص اكتمال ملف النسخة |
| تقرير بالتغييرات المتوقعة | لكل مجموعة: `countBefore`, `alreadyScoped`, `toWrite`, `unresolved`, `sampleIds`, `unresolvedIds`. يُحفظ بـ `--report out.json` | تحقق `toWrite`/`unresolved` |
| إعادة التشغيل بأمان | يتجاوز أي مستند يحمل `municipalityId`. التشغيل الثاني يكتب 0 ولا ينشئ نسخة احتياطية | «re-run is a no-op» |
| لا حذف | الكتابة إضافية فقط: `municipalityId` و`municipalityBackfilledAt` (العلامة). لا يحذف ولا يستبدل أي حقل آخر | — |
| فحص العدد قبل وبعد | `verification[col]`: `countUnchanged` (العدد ثابت) و`scopedAsExpected` (المقيَّد بعد = المقيَّد قبل + المكتوب). أي اختلاف ← `ok=false` ورمز خروج 2 | «counts verified» |
| خطة استعادة | `--restore <backup.json>` يزيل **فقط** ما أضافه الترحيل، وفقط حيث بقيت العلامة والقيمة كما كتبها. المستند الذي عُدّل بعد الترحيل يُترك ويُعدّ في `skippedChanged` | «restore undoes only its own fields» (يتحقق أن تعديلًا لاحقًا لم يُمسّ) |
| الحسابات | تقرير قراءة فقط. لا يغيّر أي مستند في `users` | يقارن `users` قبل وبعد: متطابقة |

## 3. خطوات التشغيل المقترحة (بموافقتكم، بهذا الترتيب)
1. **نسخة احتياطية كاملة للمشروع** (إضافة لنسخة الترحيل):
   ```
   gcloud firestore export gs://<bucket>/pre-scope-<date>
   ```
2. **تشغيل تجريبي** على الإنتاج بحساب خدمة قراءة. لا يكتب شيئًا:
   ```
   FIREBASE_SERVICE_ACCOUNT_JSON='…' node scripts/migrations/backfill-security-scope.mjs --report dry.json
   ```
3. **مراجعة `dry.json`:**
   - أعداد `toWrite` و`unresolved` لكل مجموعة.
   - عينة من `sampleIds`.
   - قسم `users` (§5).
4. **التطبيق:**
   ```
   … --apply --backup ./migration-backups --report applied.json
   ```
   يجب أن يطبع `verification ok: true`، وإلا توقف (رمز خروج 2) وراجع قبل المتابعة.
5. **إعادة التشغيل للتأكد:** تشغيل تجريبي ثانٍ يجب أن يُظهر `toWrite = 0` لكل المجموعات.
6. **نشر القواعد** بعد ذلك فقط (`DEPLOYMENT` في التقرير الرئيسي).
7. **عند الحاجة للتراجع:**
   ```
   … --restore ./migration-backups/backup-<ts>.json
   ```
   ثم أعد القواعد السابقة إن لزم.

## 4. نتيجة الاختبار على المحاكي
`npm run test:admin` نجح 7 من 7، ومنها اختبار الترحيل الشامل:
- **التشغيل التجريبي:** يُظهر `requests.toWrite=1` و`unresolved=1` ويكتب 0.
- **التطبيق دون نسخة احتياطية:** مرفوض.
- **التطبيق مع النسخة:** كتب 4 مستندات. التحقق ناجح، والنسخة تضم 4 تغييرات، والمستند غير المحلول لم يُخمَّن.
- **التشغيل الثاني:** كتب 0.
- **صلاحيات الطاقم بعد الترحيل:** موظف البلدية يرى الطلب المرحَّل.
- **الاستعادة:**
  - أعادت 3 مستندات وتجاوزت 1 عُدِّل بعد الترحيل، ولم تمسّ تعديله.
  - اختفى `municipalityId` و`municipalityBackfilledAt` من المستندات المستعادة.
- **الحسابات:** مستندات `users` متطابقة قبل وبعد.

## 5. سياسة مراجعة الحسابات (لا تغيير تلقائي)
يخرج الترحيل ثلاث قوائم ولا يغيّر أي حساب:

| القائمة | لماذا تهم | السياسة الموثقة |
|---|---|---|
| `statusApproved` | القواعد والمسارات الخادمية تقبل `active` فقط. الحالة `approved` القديمة **تُفقد الوصول** بعد النشر | يراجع مالك المشروع كل حساب بالاسم. إن كان صاحبه موظفًا فعليًا فيُفعَّل `setStatus: active` عبر `/api/admin/users` (يُسجَّل في التدقيق). وإن لم يُعرف صاحبه يُترك أو يُعلَّق `suspended`. **لا تحويل جماعي.** |
| `staffWithoutMunicipality` | دور طاقم (موظف/مدير/سائق) بلا بلدية يُرفض في كل شيء | يحدد مالك المشروع البلدية الصحيحة من مصدر إداري خارجي، ثم `setMunicipality` لكل حساب على حدة. المسار الخادمي يرفض تفعيل أو ترقية حساب طاقم بلا بلدية صالحة |
| `unknownRole` | دور غير معروف لا يُمنح أي صلاحية | يُصحَّح الدور يدويًا أو يُعلَّق الحساب |

السبب: تغيير الحالة أو البلدية آليًا قد يمنح صلاحية لشخص لم يعد يستحقها، أو يضع موظفًا في بلدية خاطئة فيرى بياناتها. وكلا الأمرين أسوأ من فقدان مؤقت للوصول يُصلَح بقرار بشري موثق.
