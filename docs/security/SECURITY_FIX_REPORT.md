## 2. الثغرات وأسبابها الجذرية وإصلاحها
| المعرّف | الثغرة | السبب الجذري | الإصلاح |
|---|---|---|---|
| **SEC-01 (P0)** | موظف يغيّر دوره أو يرقّي غيره | فرع تحديث `users` للموظفين لا يستثني `role` و`status`، وينطبق على المستند الشخصي | العميل لا يكتب `role` و`status` و`municipalityId` و`homeMunicipalityId` و`transferId` و`transferUntil` و`roleAr` و`uid` أبدًا، **حتى الأمانة**. التغيير عبر `POST /api/admin/users` بعد التحقق من رمز Firebase ومن أن المنفذ «متخذ قرار بالأمانة» **نشط**، مع منع تغيير الدور أو الحالة الذاتية وتدقيق من الخادم |
| SEC-02 (P1) | قراءة بيانات المستخدمين عبر البلديات | قراءة `users` بشرط `isEmployee()` وحده | القراءة: المستخدم نفسه، والأمانة، ومدير أو موظف **بلديته** فقط |
| SEC-03 (P1) | حساب طاقم بلا بلدية يحصل على المدينة كاملة | `sameMun()` تعيد true حين يغيب `municipalityId`، ولا تحقق من صحة الدور | **Fail Closed:** دور معروف + حالة `active` + بلدية غير فارغة لكل دور غير `executive`. الدور غير المعروف أو الغائب والملف الغائب بلا وصول |
| SEC-04 (P1) | كتابة عابرة للبلديات (أحياء، حساسات حريق، تنبيهات، تحليلات، قراءات محاكاة) | مجموعات بلا شرط بلدية، ومرجعيات قابلة للكتابة من أي موظف | `inMun()` / `staysInMun()` على كل مجموعة تشغيلية. حساسات الحريق والتحليلات والمحطات للأمانة فقط. قراءة المحاكاة تشترط بلدية الكاتب ووسم المحاكاة |
| SEC-05 (P1) | تزوير سجل التدقيق وانتحال النظام | الإنشاء `isStaff()` دون ربط الفاعل بالهوية | `actorId == auth.uid`، وحظر أسماء النظام المحجوزة، و`municipalityId` = بلدية الفاعل، ولا تعديل، ولا حذف إلا لصفوف العرض من الأمانة. سجلات القرارات الحساسة (الأدوار والبلديات والإسناد التلقائي) يكتبها الخادم |
| SEC-06 (P1) | سجل أجهزة IoT مقروء ومكتوب على نطاق واسع | قراءة `isStaff()` (تشمل السائقين)، وكتابة `isEmployee()` بلا بلدية | القراءة والكتابة للأمانة، أو لمدير بلدية الجهاز فقط. إعادة الربط تشترط أن الحاوية الجديدة في بلديته |
| ISO-01 (P1) | البلاغات والطلبات غير مقيّدة | استعلام بلا فلتر، ومستندات بلا `municipalityId` | حقل البلدية عند الإنشاء (من الحي)، وقواعد `inMun`، واستعلام الصفحة مقيّد، وترحيل للقديم |
| SEC-09 (P2) | صلاحيات السائق أوسع من اللازم | انتقالات حالة غير مقيدة، وتأكيد لأي حاوية | المسار `approved → in_progress → completed` فقط. التأكيد لحاوية **ضمن جولته**. البلاغ على جولته. سجل الحالة لمركبته. ختم الجمع داخل بلديته |

**المسار الخادمي** (`tests/integration/admin.users.test.mjs`، 7 من 7، محاكيان معزولان مع رموز Auth حقيقية):
- بلا رمز: 401. موظف العمليات ومدير البلدية والسائق وحساب أمانة موقوف: 403.
- لا تغيير ذاتي للدور أو الحالة، حتى للأمانة.
- لا تفعيل لحساب طاقم بلا بلدية، ولا بلدية أو دور غير معروفين.
- التغيير المشروع يُكتب ومعه تدقيق خادمي (`source: "server"`).
- التغيير نفسه من SDK العميل مرفوض لكل الأدوار.
- إعادة توطين حساب السائق تتم فقط لنقل منفَّذ، والإرجاع فقط لنقل مُعاد.
- الترحيل: التجريبي لا يكتب، والتطبيق ينطاق المستندات، وإعادة التشغيل لا تكتب شيئًا، وطاقم البلدية يرى المستندات بعده.

## 5. العمليات المصرح بها (عدم التراجع)
41 عملية مشروعة في الجدول. أمثلة:
- **مدير البلدية:** يقرأ ويسرد مستخدمي بلديته وأجهزتها وسجلها وسيناريوهاتها، ويعدّل أحياءها.
- **موظف العمليات:** يعتمد جولات بلديته، ويحدّث مركباتها، ويرد على طلباتها، ويغلق استثناءاتها، وينشئ تنبيهاتها.
- **السائق:** يبدأ جولته، ويؤكد تفريغ حاوياتها، ويرفع بلاغ جولته، ويغيّر مناوبته.
- **الأمانة:** تسرد كل شيء، وتقترح النقل، وتغيّر وضع الإسناد، وتحدّث الحساسات المرجعية.
- **المواطن:** يعدّل ملفه دون الحقول الحساسة، وينشئ طلباته وبلاغاته ويقرؤها.

## 8. إعداد خارجي مطلوب قبل النشر (بموافقتكم، بهذا الترتيب)
1. **حساب الخدمة:** `FIREBASE_SERVICE_ACCOUNT_JSON` في Vercel. **لوحة إدارة المستخدمين ونقل السائقين يعتمدان عليه الآن.** بدونه ترد `/api/admin/users` بـ 500.
2. **ترحيل بيانات الإنتاج:** `node scripts/migrations/backfill-security-scope.mjs` تجريبيًا، ثم `--apply` بحساب الخدمة. يجب أن يسبق نشر القواعد، وإلا اختفت البلاغات والتنبيهات والأجهزة القديمة عن طاقم البلديات.
3. **مراجعة حسابات الإنتاج:** كل حساب طاقم يحتاج `municipalityId` صالحًا وحالة `active` بالضبط. حسابات بحالة `approved` أو بلا بلدية ستفقد الوصول عمدًا. تُصحَّح من لوحة المستخدمين.
4. **دفع الكود:** يحوي المسار الخادمي والاستعلامات المقيّدة.
5. **نشر القواعد:** `firebase deploy --only firestore:rules`، ثم `npm run test:security` على مشروع اختبار منشور.

## 9. تقييم الجاهزية الأمنية للنشر
- **قواعد Firestore:** **جاهزة للنشر تقنيًا.** الثغرة الحرجة P0 وثغرات P1 المثبتة كلها مغلقة باختبارات قابلة لإعادة التشغيل، دون كسر أي وظيفة مختبرة.
- **النشر نفسه:** مشروط بالخطوات 1 إلى 5 أعلاه وبموافقتكم.
- **ما يبقى قبل اعتبار المنصة جاهزة أمنيًا للإنتاج العام:**
  - حد معدل الطلبات (SEC-07).
  - سياسة كلمات المرور وMFA للأدوار الإدارية (SEC-10).
  - إغلاق وكلاء الذكاء الاصطناعي (SEC-11).
  - CI يشغّل هذه الاختبارات قبل كل نشر (OPS-02 في تقرير التدقيق).
