## 2. الأدلة والاختبارات

### اختبار جديد: `npm run test:guards`
21 نجاح من 21. الملف `tests/integration/server.guards.test.mjs`، ويعمل على محاكيي Firestore وAuth مع القواعد الحقيقية ورموز هوية حقيقية.

| الحالة المطلوبة | الاختبار | النتيجة |
|---|---|---|
| سائق يؤكد حاوية خارج جولته | `confirm: a bin that is NOT on the driver's route` → 409، ولا حدث مكتوب | ✓ |
| سائق يؤكد في جولة غير مسندة له | `a route assigned to ANOTHER driver` → 403 | ✓ |
| تكرار التأكيد | `repeated confirmation is idempotent`: حدث واحد، والوقت الأصلي محفوظ، وسجل تدقيق واحد | ✓ |
| التأكيد قبل بدء الجولة | `before the route is started` → 409 «ابدأ الجولة…» | ✓ |
| فشل نقل الموارد في منتصف العملية | فشل مُحقن بعد **كل** خطوة (vehicle, profile, user, transfer, audit): الحالة مطابقة حرفيًا لما قبل، ولا تدقيق | ✓ |
| طلب إداري دون صلاحية | مدير وسائق على `/api/admin/transfers` و`/api/admin/users` → 403 مع `access_denied` | ✓ |
| تجاوز حد الطلبات | 429 مع `Retry-After` لكل من التأكيد والإدارة والإسناد والذكاء الاصطناعي، والعدّاد في Firestore | ✓ |
| وكيل ذكاء اصطناعي يصل لبلدية أخرى | سياق مدير الشرق لا يحوي حاوية الشمال (والعكس) رغم طلب صريح بتجاهل التعليمات. طلب `municipalityId`/`system`/`tools`/`model` → 400. لا أدوات تصل للنموذج | ✓ |

وحالات إضافية في الملف نفسه:
- مركبة في الصيانة وتوقف متخطى → 409.
- موظف، أو حقل غير معروف، أو بلا رمز، أو حساب `approved` → 403/400/401/403.
- فشل مُحقن في كل خطوة تأكيد لا يترك أثرًا.
- السائق والموظف لا يتجاوزان الخادم عبر SDK.
- نقل لمورد مشغول → 409 دون نقل.
- السائق يرى جولاته فقط، والمواطن طلباته فقط في سياق الذكاء الاصطناعي.

## 4. تقرير سلامة نقل الموارد

- **التصميم:** `runTransfer` معاملة واحدة.
  - **القراءات أولًا:** النقل، المركبة، ملف السائق، الحساب، الجولات النشطة للمركبة والسائق.
  - **ثم التحقق:**
    - الحالة `approved` للتنفيذ و`executed` للإعادة.
    - كل مورد في البلدية المتوقعة.
    - لا مورد على جولة جارية أو معتمدة.
  - **ثم الكتابة في المعاملة نفسها:**
    - المركبة والملف والحساب: `municipalityId` و`homeMunicipalityId` و`transferId` و`transferUntil`.
    - حالة النقل.
    - سجل التدقيق.
- **حالات جزئية:** مستحيلة بنيويًا. Firestore يطبّق كل الكتابات أو لا شيء. أُثبت ذلك بحقن فشل بعد كل خطوة من الخمس، ومقارنة حالة الموارد الأربعة حرفيًا قبل وبعد.
- **التزامن:** المعاملة تعيد المحاولة عند تعارض الكتابة، فيُتوقع أن ينتهي تنفيذان متزامنان بتنفيذ واحد والآخر بـ `already: true`. هذا مبني على ضمان Firestore؛ الاختبار يغطي التكرار المتتابع لا المتزامن.
- **التصحيح اليدوي:** لم يعد مسارًا أساسيًا. `setMunicipality` مرفوض لحساب في نقل جارٍ حتى لا يُكسر الاتساق يدويًا.
- **حدود معروفة:** `transferUntil` يُسجَّل لكن **لا إعادة تلقائية عند انتهاء المدة**. الإعادة قرار من الأمانة، كما كان سابقًا.

## 7. متطلبات النشر (بموافقتكم فقط، بهذا الترتيب)
1. **متغيرات Vercel** (خادم فقط، **بلا** بادئة `VITE_`):

   | المتغير | الاستخدام | أثر غيابه |
   |---|---|---|
   | `FIREBASE_SERVICE_ACCOUNT_JSON` | كل المسارات الخادمية | تأكيد التفريغ والنقل والإدارة ترد 500 |
   | `GROQ_API_KEY` | المساعد الذكي | يرد 503، فيُعطَّل المساعد بأمان |
   | `CRON_SECRET` | الجدولة كل 15 دقيقة | الجدولة لا تعمل |
   | `RATE_LIMITS` | تعديل الحدود (اختياري) | تُستخدم الحدود الافتراضية |

2. **سياسة TTL** على `rate_limits.expiresAt` (Timestamp) من Firebase Console أو `gcloud firestore fields ttls update`، لتنظيف النوافذ القديمة.
3. **الترحيل** وفق `MIGRATION_READINESS.md`، ثم مراجعة الحسابات.
4. **دفع الكود** إلى الفرع الذي يُنشر منه Vercel. **يجب أن يسبق نشر القواعد أو يتزامن معه**، لأن القواعد الجديدة تمنع كتابة التأكيد من العميل القديم. السائقون بالنسخة القديمة يجب تحديث صفحاتهم. التأكيدات المحفوظة في طابور النسخة الجديدة دون اتصال تُرسل عبر الخادم؛ أما طابور محفوظ بالنسخة القديمة فلم يُختبر عبر الترقية، فيُفضّل النشر في وقت لا جولات جارية فيه.
5. **نشر القواعد:** `firebase deploy --only firestore:rules`.
6. **فحص بعد النشر:**
   - `npm run test:security` على مشروع اختبار (ليس الإنتاج).
   - تأكيد تفريغ واحد على حاوية محاكاة.
7. **إزالة القيمة القديمة** `groq_api_key` من متصفحات المستخدمين: تتم تلقائيًا عند فتح بطاقة الإعدادات.
