| المجال | موجود قبل هذه المرحلة | ناقص / ضعيف |
|---|---|---|

| **التوجيه** | عميل OSRM عام (`roadRouting.js`) بمسار GeoJSON ومسافة وزمن، بذاكرة مؤقتة وإلغاء | بدون `steps` (لا مناورات)؛ خادم OSRM عام غير مضمون للإنتاج؛ لا حل VRP |
| **بوابة السائق** | ترتيب الأحياء بمسافة الطريق من موقع GPS (`getCurrentPosition` مرة واحدة)، معاينة مسار على الطرق، بدء/تفريغ/تخطي/إنهاء، بلاغ عطل/عائق كسجل تدقيق | لا `watchPosition`؛ لا متابعة الخريطة؛ لا ملاحة خطوة بخطوة؛ لا كشف انحراف؛ لا منع تكرار الضغط؛ التخطي يُسجَّل كـ"مجموعة" (`collectedBinIds`) وهو خطأ تصميمي يُصحَّح في المرحلة 5 |
| **تنفيذ الجمع** | `recordCollectionEvent` يكتب حدث تفريغ ويحدّث `lastCollectionAt` فقط ولا يلمس قراءات المستشعر ✅ | موقع التأكيد ودقته غير مسجلين؛ حدث التفريغ بلا `driverId` صريح |
| **المتابعة** | لوحة تحكم، تقارير أداء السائقين/المركبات من الجولات المكتملة | لا مواقع مركبات حية؛ لا لوحة عمليات للأسطول |
| **الأمان** | قواعد مسودّة تفصل قراءات المستشعرات عن العملاء؛ مفاتيح الأجهزة مُجزَّأة | القواعد غير منشورة؛ السائق مسموح له قراءة كل الجولات |
| **الاختبارات** | 93 اختبار وحدة (قرار، تنبؤ، تنبيهات، أثر، خريطة، مسارات ميدانية) | لا اختبارات للأسطول أو الصلاحيات أو قواعد Firestore |

## ثانيًا: المعمارية

### طبقات
```
UI (App.jsx)  ──►  محركات نقية بلا React/Firestore  ──►  خدمة البيانات (firestoreService.js)  ──►  Firestore + rules
                    ├─ decisionEngine.js  (أولوية، أهلية الجمع، اقتراح الجولات)
                    ├─ prediction.js      (معدل الامتلاء، التنبؤ)
                    ├─ fleetEngine.js     (RBAC، إسناد، تعارض، تغطية)        ← المرحلة 1
                    ├─ assignmentEngine   (ترشيح السائق بالوقت الحقيقي)      ← المرحلة 2
                    ├─ routeOptimizer     (VRP موزون بالسعة والأولوية)        ← المرحلة 3
                    ├─ navigation         (مناورات، انحراف، إعادة توجيه)      ← المرحلة 4
                    └─ roadRouting.js     (مزود توجيه قابل للاستبدال: OSRM/Valhalla/GraphHopper)
```
القواعد: المحركات دوال نقية مختبَرة بـvitest؛ الواجهة لا تعيد اشتقاق أي قاعدة؛ القواعد الأمنية تعكس `fleetEngine.can()` سطرًا بسطر.

### تدفق العمليات المستهدف
1. الحاويات ↔ المستشعرات → محرك القرار يولّد **مقترح مهمة** لكل حي فيه حاويات مؤهلة (موجود).
2. محرك الإسناد يرشّح سائقًا: نطاق ∩ مناوبة ∩ توفر ∩ مركبة صالحة ∩ سعة ∩ زمن وصول بالطرق (المرحلة 1 جزئيًا، 2 كاملة).
3. المدير يراجع ويعتمد → الجولة تحمل `driverId/vehicleId` → تصل لحساب السائق **وحده** (المرحلة 1 ✅).
4. السائق يبدأ المناوبة → يبدأ الجولة → ملاحة خطوة بخطوة → يؤكد التفريغ من موقعه → عوائق تُبلَّغ وتعاد الجدولة (المراحل 4–5).
5. المدير يتابع الأسطول حيًا ويرى البلاغات (المرحلة 5).

### نموذج البيانات (Firestore)
| المجموعة | الحقول الأساسية | ملاحظة |
|---|---|---|
| `users/{uid}` | role, status | موجودة؛ لم تُمس |
| `driver_profiles/{uid}` ✅ | driverCode, fullName, phone, accountStatus, shiftStatus, availability, vehicleId, neighborhoodKeys[], shiftStart/End, locationSharing, lastLocation{lat,lng,accuracy,heading,at}, currentRouteId, stats | id = uid؛ السائق يعدّل حقول المناوبة/الموقع فقط |
| `driver_vehicle_assignments` ✅ | driverId, vehicleId, start, end|null, active, assignedBy, reason | نوافذ زمنية؛ لا حذف؛ التعارض يُفحص قبل الكتابة |
| `driver_assignment_history` ✅ | driverId, fields[], before{}, after{}, actorId, reason | كل تعديل إداري |
| `driver_shifts` ✅ | driverId, status, at | بدء/إنهاء/استراحة |
| `driver_locations` (م4) | driverId, routeId, lat, lng, accuracy, heading, speed, at | يُكتب فقط أثناء المناوبة؛ احتفاظ 7 أيام (حذف مجدول) |
| `collection_routes` ✅ | + driverId, driverName, assignmentException{reason,by,at} | `route_stops` تبقى مضمّنة في `orderedStops` (حجم صغير، قراءة واحدة) |
| `collection_events` | + driverId, confirmLocation{lat,lng,accuracy}, idempotencyKey (م5) | مفصولة عن `sensor_readings` كليًا |
| `route_incidents` (م5) | routeId, binId, driverId, type(obstacle/fault/unreachable), note, location, status, reviewedBy | تحل محل سجل التدقيق كمصدر للبلاغات |
| `vehicle_status_history` (م5) | vehicleId, from, to, by, at | |
| `audit_log` ✅ | action, actorId, details | موجود؛ أُضيفت 8 أفعال |

**الفهارس المطلوبة** (`firestore.indexes.json` في المرحلة 2): `collection_routes(driverId, status)`، `driver_locations(driverId, at desc)`، `route_incidents(status, createdAt desc)`.

### قيود السلامة
- مركبة واحدة لسائق في أي لحظة، وسائق واحد لمركبة في أي لحظة (`findVehicleAssignmentConflicts`).
- جولة نشطة واحدة لكل سائق، وجولة نشطة واحدة لكل مركبة (`findRouteAssignmentConflicts`).
- السائق يقرأ ويعدّل فقط الجولات التي `driverId == uid` (قاعدة Firestore + استعلام مقيّد `useMyRoutes`).
- الإسناد الاستثنائي ممكن فقط بمبرر مكتوب يُحفظ على الجولة وفي سجل التدقيق.

### قيود يجب قولها بصراحة
- **تتبع GPS في الخلفية**: متصفحات الجوال توقف `watchPosition` عند إقفال الشاشة أو تبديل التطبيق (خصوصًا iOS Safari). الحل الواقعي: PWA مثبّت + إبقاء الشاشة نشطة (`Wake Lock API`) أثناء الملاحة، وقبول فجوات في المسار. التتبع الحقيقي في الخلفية يحتاج تطبيقًا أصليًا.
- **OSRM العام** (`router.project-osrm.org`) للتجارب فقط ولا يضمن توفرًا ولا حدودًا. للإنتاج: استضافة OSRM/Valhalla على خادم صغير بخريطة السعودية، والعميل الحالي معزول في `roadRouting.js` فاستبداله سطر واحد.
- **الملاحة خطوة بخطوة** ستعتمد على مناورات OSRM التي لا تتضمن اتجاهات السير الممنوعة محليًا ولا أعمال الطرق؛ تُعرض كإرشاد مساعد لا كبديل عن انتباه السائق.
- **OR-Tools** لا يعمل في المتصفح؛ تشغيله يتطلب Function بايثون على Vercel أو خدمة منفصلة. للحجم الحالي (≤ 15 حاوية للجولة) البحث المحلي المنفَّذ كافٍ ونتائجه قابلة للتحقق. المحرك يحل مركبة واحدة لكل جولة (الجولات مقسمة بالأحياء أصلًا)؛ توزيع متعدد المركبات عبر الأحياء غير مطلوب الآن.
- **نقاط التفريغ** غير معرفة في البيانات بعد (حقول `dumpLat/dumpLng/dumpLabel` اختيارية على المركبة)؛ حتى تُضاف يُبلّغ المحرك صراحة أن الحمولة الزائدة تُؤجَّل بدل اختلاق رحلة تفريغ.

## قيود معلنة بعد التنفيذ (المراحل 4–6)
- **التتبع في الخلفية**: `watchPosition` يتوقف عند قفل الشاشة أو تبديل التطبيق على iOS Safari وبعض أندرويد. الحل الواقعي: تثبيت كـPWA + إبقاء الشاشة نشطة أثناء الملاحة (Wake Lock)، وقبول فجوات. تتبع خلفي حقيقي يحتاج تطبيقًا أصليًا.
- **الملاحة**: الإرشادات من مناورات OSRM (بلا مسارات حارات، بلا حركة مرور حية، بلا أعمال طرق). تُعرض كمساعدة؛ لا تُحجب أي عملية على السائق إن غابت.
- **الصوت**: يعمل فقط إن وفّر الجهاز صوتًا عربيًا في Web Speech؛ وإلا تظهر ملاحظة ويبقى الإرشاد المرئي.
- **المراقبة**: الأخطاء تُسجَّل في console وتُحفظ العمليات الفاشلة في الطابور المحلي؛ لا يوجد بعد تجميع مركزي للأخطاء (Sentry أو ما يماثله) — يُضاف عند النشر.
- **الاحتفاظ بالموقع**: `driver_locations` تحمل `expiresAt` (7 أيام) لكن حذفها يحتاج سياسة TTL أو وظيفة مجدولة تُفعَّل عند النشر.
- **قواعد Firestore** مختبَرة على المحاكي لكنها **غير منشورة**: `firebase deploy --only firestore:rules`.

## ما ينفَّذ في المرحلة 1 (ملخص تقني)
- `src/fleetEngine.js`: `can()` مصفوفة RBAC، `validateDriverProfile`، `findVehicleAssignmentConflicts`، `findRouteAssignmentConflicts`، `eligibleDriversFor` (مع أسباب الاستبعاد)، `coverageMatrix`، `locationFreshness`.
- `src/firestoreService.js`: المجموعات الأربع الجديدة + `useMyRoutes(uid)` + `useMyDriverProfile` + `approveAndAssignRoute`.
- `firestore.rules`: قواعد `driver_profiles/driver_vehicle_assignments/driver_assignment_history/driver_shifts`، وتقييد قراءة/تعديل `collection_routes` للسائق إلى جولاته.
- الواجهة: صفحة «السائقون والأسطول»، اختيار السائق في اعتماد الجولة، بوابة السائق تعرض ملفه ومناوبته وجولاته فقط.

**ما لا تفعله المرحلة 1**: لا تحسب زمن الوصول للمرشحين (م2)، لا تغيّر ترتيب التوقفات (م3)، لا تتبّع الموقع المستمر (م4).

**للتشغيل الفعلي بعد الاعتماد**: `firebase deploy --only firestore:rules` (بعد مراجعة القواعد)، ثم تفعيل حسابات السائقين من إدارة المستخدمين وتهيئة ملفاتهم.
